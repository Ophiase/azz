# Local Ids — referring to work items that do not exist yet

**Date:** 2026-07-31
**Status:** Accepted
**Builds on:** [2026-07-24-plan-engine.md](./2026-07-24-plan-engine.md)

---

## Context

The plan engine lets an agent author a batch of new work items as
`.azz/tasks/*.md` files with no `item_id`, and the human pushes them. The
intended workflow is: give Claude a task id, let it detail that task's file
and add new files alongside.

Adding a *tree* of new items is the case that breaks. A new child needs to
name its new parent, and neither of them has a remote id yet — the ids only
come into existence during `push`.

Today `parent` is typed `int | None`, so this is not merely unspecified, it
is impossible:

```text
parent: 7412        → OK   parent=7412
parent: auth-epic   → FAIL 1 validation error for LocalItem
```

It fails loudly rather than corrupting anything, which is the right failure.
But it blocks the workflow the plan engine exists to serve.

---

## Decision

Add `local_id`: a human-chosen slug, unique across `.azz/tasks/`. Let `parent`
accept either type, disambiguated by YAML's own typing.

```markdown
<!-- .azz/tasks/auth-epic.md -->
---
local_id: auth-epic
title: Authentication overhaul
type: Epic
---

<!-- .azz/tasks/login-page.md -->
---
local_id: login-page
parent: auth-epic
title: Implement login page
---

<!-- .azz/tasks/fix-redirect.md -->
---
parent: 7412
---
```

- An **integer** `parent` is a remote work item id, exactly as today.
- A **string** `parent` names another file's `local_id`.
- `local_id` is optional. A file only needs one if something references it.

After `push`, `parent` is rewritten to the real integer — consistent with the
existing `item_id` and title write-back, which already keep files canonical.
`local_id` is left in place as a stable handle.

### Why a readable slug and not a generated id

The alternative considered was a sentinel, `parent: "#tb-382908-939328"`.
Random ids exist to avoid collisions without coordination. Here there is no
coordination problem: every intent file is in one directory, so two files
claiming the same `local_id` is detectable at parse time and becomes an error
before anything is pushed. Randomness buys nothing and costs a great deal of
readability — `parent: auth-epic` is far harder to get wrong than matching up
two long digit strings, for a human and for an agent.

### Why not the filename

Filenames are already unique, so `parent: login-page` meaning `login-page.md`
needs no new field at all. Rejected for three reasons: the 2026-07-24 record
deliberately made the filename a human label with **no machine meaning**;
renaming a file would silently break references; and `fetch` writes
`<id>-<slug>.md`, so fetched and hand-authored files would not follow the
same rule.

### Why not a separate `parent_local` field

Two fields would remove the need to disambiguate by type. Rejected as the
worse trade: it adds a key to the format's vocabulary and makes "this item
has a parent" a question you have to ask twice. Int-versus-string is free in
YAML and reads as self-documenting.

The one sharp edge accepted here: `parent: "7412"` — quoted, so a string —
is read as a `local_id` and fails with "no intent file declares local_id
7412". That message is clear enough to diagnose in one read.

### Why not pre-allocate real ids

Azure DevOps can create an item and return its id, so `push` could create
placeholder items up front and use real ids throughout. Rejected: it puts
half-formed items on the board before the human has approved anything, which
is precisely what the plan engine exists to prevent.

---

## Consequences

These are the parts that are easy to miss, and each is a real change rather
than a detail.

**`push` needs a topological sort.** Creates currently run in whatever order
the files sort in. Parents must be created before their children so the real
id exists when the child is linked. Cycles must be rejected up front, before
any remote call — a cycle discovered halfway through leaves a partly created
tree.

**Failures must propagate down the tree.** The applier currently reports an
error and continues to the next item. If a parent fails to create, its
descendants must be *skipped* with a clear reason, not created as orphans and
not linked to a stale id. This is the change most likely to be got wrong,
because the current "keep going" behaviour is otherwise correct and
deliberate.

**Dangling references are a `status`-time error.** A `parent` slug matching no
file must be reported by `azz plan status`, before `push` runs. Validation
belongs where the whole set of files is visible, not in the per-file parser.

**`status` should resolve local parents when rendering.** `will create Task`
is unhelpful for a child; it should read `will create Task under auth-epic
(new)` so the tree is visible before it is built.

**Depth is not special.** A chain of three or more new items follows from the
topological sort with no extra work. Worth stating because it is the case
most likely to be left untested.

---

## Verdict

`local_id` plus a dual-typed `parent`. No sentinel syntax, no filename
coupling, no pre-allocated remote ids.

The format cost is one optional key. The implementation cost is concentrated
in `push`: a topological sort, and failure propagation down the tree. That
second one is the part to review carefully.
